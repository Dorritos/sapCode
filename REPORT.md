# REPORT — САП КОД AI-разработчик

Дата: 23 октября 2026 года.

## 1. Что было сломано

Каждая доставка сообщения создавала новую заявку и уведомление, включая
повтор той же пары `(source, external_id)`. Обязательные поля не проверялись,
пробелы по краям сохранялись, статусы `duplicate` и `invalid` не возвращались.
На Windows незакрытые подключения в приложении и вспомогательном коде тестов
вызывали ошибки удаления временных баз.

Исходный запуск и найденные проблемы зафиксированы в [REPORT_BEFORE.md](REPORT_BEFORE.md).

## 2. Что исправлено

- Четыре обязательных поля проверяются до обращения к базе: только строки,
  непустые после `strip()`. Некорректное событие возвращает `invalid`
  с понятной причиной и не меняет сохранённые записи.
- Пробелы по краям всех полей удаляются перед сравнением и сохранением;
  регистр сохраняется.
- Уникальный индекс закрепляет пару `(source, external_id)`.
  `INSERT ... ON CONFLICT ... DO NOTHING` позволяет вернуть существующий id
  при повторе, сохранив первоначальные customer/message.
- Новая заявка и её единственное уведомление записываются одной транзакцией.
  При ошибке записи уведомления новая заявка откатывается.
- Подключения явно закрываются. В двух местах исходных тестов исправлено
  только управление подключением; все исходные проверки сохранены.

Сохранены обе исходные функции, сигнатура публичной функции, таблицы,
столбцы и стандартная библиотека Python. Архитектура остаётся прежней:
один файл обработчика, SQLite и unittest.

Результат штатного запуска на Python 3.14.9:


В исходном запуске один тест мог иметь и провал проверки, и ошибку очистки;
это не 13 отдельных тестов.

Добавлены шесть тестов:

1. Проверка каждого обязательного поля: отсутствие, None, число, bool,
   список, словарь, пустая и пробельная строка. Всего 32 случая через subTest;
   существующие заявка и уведомление остаются без изменений.
2. Удаление пробелов, табуляции и перевода строки по краям всех четырёх полей
   при сохранении; положительный id.
3. Различение источников `telegram` и `Telegram`.
4. Разные external_id в одном источнике создают разные заявки.
5. Значение события, не являющееся словарём, возвращает `invalid`.
6. Искусственная ошибка записи уведомления откатывает новую заявку и сохраняет
   ранее созданные данные. Триггер для ошибки существует только во временной
   базе этого теста.

Дополнительно выполнены:

- Сравнение исходных и конечных тестов через AST: все восемь исходных методов
  и их assertions сохранены.
- Проверка неизменности README.md, ASSIGNMENT.pdf, REPORT_TEMPLATE.md
  и .gitignore относительно исходного коммита.
- Проверка записей после повторов: остаются одна заявка, одно уведомление

## 6. Оставшиеся ограничения и риски

Миграция старой базы, в которой уже накоплены дубли одной пары source/external_id,
в задании не определена и не реализована: создание уникального индекса для
такой базы вернёт ошибку, существующие строки не удаляются. Проверка сохранности
при переоткрытии корректной базы проходит.

Ошибки доступа к файлу и другие эксплуатационные ошибки SQLite не маскируются
статусом `invalid`: этот статус относится к данным события. Все проверки
выполнены на синтетических данных во временных базах.
